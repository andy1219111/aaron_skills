**Writing Tech Docs** 是一套面向研发团队、产品、架构师的**标准化技术文档生产体系**。依托原始会议纪要、需求矩阵、调研报告、标书、SQL 脚本等多源素材，规范产出 PRD、SRS、系统设计、概要设计、详细设计等工程文档，严格遵循**内容可追溯、信息不编造、图表先草图**三大核心原则。

## 📖 项目简介
在日常研发协作中，技术文档常存在**结构混乱、信息缺失、内容杜撰、来源不可查、图表与需求不符**等问题。
本项目提炼出一套**8阶段串行式标准化流程**，强制规范从原始素材到正式文档的全链路动作，同时配套置信度标记、交叉校验、需求追溯、图表草图预审等机制，保证输出文档严谨、合规、可落地。

核心优势：
1. **全链路可追溯**：每一段内容、参数、规则均绑定原始素材来源
2. **拒绝虚构内容**：信息缺失统一标记 `TODO`，不脑补、不猜测
3. **流程强约束**：关键节点必须经使用者确认，提前规避理解偏差
4. **多源兼容**：支持会议纪要、需求矩阵、投标文件、研究报告等异构素材整合
5. **图表标准化**：统一绘图流程与工具选型，杜绝图文不一致

## 🎯 适用范围
### 支持文档类型
- 产品需求文档：PRD
- 软件需求规格说明书：SRS
- 系统总体设计文档
- 概要设计文档
- 详细设计文档
- 技术方案、投标技术文档、接口规范文档

### 适用场景
1. 基于**多份原始素材**整合生成正式技术文档
2. 梳理零散需求、会议内容，输出结构化交付文档
3. 团队统一文档编写规范，提升文档质量与一致性
4. 需要搭配架构图、流程图、时序图、部署图等可视化图表
5. 识别多源信息冲突、补充信息缺口、建立需求追溯关系

### 不适用场景
1. 纯代码开发、缺陷修复、单文件代码编辑类任务
2. 仅做文档翻译、格式美化、排版调整（无内容创作）
3. 无任何原始依据、纯凭空创作的文档

## ⚖️ 核心设计原则
1. **无源不落笔**：文档所有描述、参数、规则必须能溯源至原始素材，无来源内容禁止编写
2. **缺项必标记**：素材缺失、信息不足的部分统一标注 `[TODO]`，严禁编造内容补齐
3. **图表先草图**：任何可视化图表，必须先输出纯文本草图并确认，再使用工具绘制
4. **流程不跳步**：8大阶段必须按顺序串行执行，禁止随意跳过合并环节
5. **冲突必显式**：多份素材内容不一致时，完整展示各方描述，交由使用者裁决

## 🚀 八大标准工作流程
> 强制要求：**按顺序执行，不可跳过任一阶段**；带 ✅ 标记节点必须等待用户确认后再推进

| 阶段 | 阶段名称 | 核心工作 | 交付物 | 是否需要确认 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 素材盘点 | 收集、梳理全部原始素材，标注路径、类型、日期、相关性，确认无遗漏 | 结构化素材清单 | ✅ 是 |
| 2 | 模板选择 | 优先复用项目现有模板；无模板则匹配文档类型提供标准结构 | 确认后的文档结构/模板 | ✅ 是 |
| 3 | 信息提取与交叉核对 | 拆解素材内容，提取需求、约束、依赖、风险；建立交叉核对矩阵，识别冲突与缺口 | 信息提取表 + 冲突/缺口清单 | ✅ 是 |
| 4 | 带标记大纲 | 基于模板生成完整大纲，每章节标注**来源 + 置信度** | 带标注、缺口标记的完整大纲 | ✅ 是 |
| 5 | 图表设计 | 梳理配图章节 → 确认绘图工具 → 输出文本草图 → 确认后生成正式图表 | 文本草图 + 最终图表文件 | ✅ 是 |
| 6 | 逐节内容编写 | 依据大纲与素材逐段编写，缺失/不确定内容统一标记 | 带标记的完整文档正文 | ❌ 否 |
| 7 | 完整性校验 | 构建需求追溯矩阵，核对参数、章节覆盖度，从使用者视角自检疑问点 | 需求追溯矩阵 + 校验报告 | ❌ 否 |
| 8 | 输出与元数据 | 导出最终文档，补充版本、素材、完整性评分等元数据，汇总待办项 | 最终文档 + 元数据报告 + TODO 清单 | ❌ 否 |

## 🏷️ 信息置信度规范
全文档统一使用以下标记标注信息状态，**所有章节必须附带标记**：

| 标记 | 状态说明 | 执行规则 |
| :---: | --- | --- |
| ✅ 充分 | 原始素材信息完整、细节齐全 | 正常编写完整内容 |
| ⚠️ 部分 | 素材有相关描述，但关键细节缺失 | 编写已有内容，显性标注信息缺口 |
| ❌ 不足 | 模板要求该章节，但素材无任何对应内容 | 仅保留章节标题，标注 `[TODO]`，不编造内容 |
| ⚡ 矛盾 | 多份素材对同一内容描述不一致 | 并列展示所有版本，等待使用者确认统一口径 |

## 📊 图表设计规范
### 1. 可用工具优先级
`drawio` > 专用架构图工具 > Mermaid > 原生 SVG
> 兜底方案：若无专业绘图工具，**Mermaid / SVG 永久可用**，不得以“无工具”为由跳过图表环节。

### 2. 章节与图表匹配建议
| 文档章节 | 推荐图表类型 | 适配工具 |
| --- | --- | --- |
| 系统架构 | 系统架构图 | drawio / SVG |
| 模块拆分 | 组件图 | drawio / Mermaid |
| 网络/机房部署 | 拓扑图、部署图 | drawio / SVG |
| 业务/数据流转 | 数据流图、流程图 | Mermaid / drawio |
| 接口交互 | 接口关系图、时序图 | Mermaid / drawio |

### 3. 强制绘图流程
1. 扫描大纲，筛选需要配图的章节
2. 确认绘图工具与配图范围
3. 输出 **纯文本 ASCII 草图** 供审核
4. 草图确认无误后，再绘制正式图表
5. 将图表嵌入文档对应章节

> 特殊说明：使用者明确表示「无需配图」，可直接跳过本阶段。

## 🛑 红线约束 & 常见错误
### 🔴 绝对红线（出现立即停止工作，回退至对应阶段）
1. 未确认模板/文档结构，直接开始编写正文
2. 大纲标记 `❌ 信息不足`，仍强行填充内容
3. 使用「大概、可能、通常」等模糊词汇定义硬性参数
4. 无法指明内容对应的原始素材来源
5. 虚构数据、规则、功能填补信息缺口
6. 跳过文本草图，直接生成正式图表
7. 以「文档简单、时间紧张」为由跳过任一标准阶段

### 🐛 高频错误与修复方案
| 常见错误 | 产生原因 | 修复方案 |
| --- | --- | --- |
| 凭经验直接编写，不使用模板 | 主观认为结构固定 | 严格执行「模板选择」阶段，先定结构再写作 |
| 读完素材直接动笔，不做信息提取 | 缺少标准化拆解动作 | 强制执行信息提取与交叉核对，梳理后再写作 |
| 写作过程中才发现信息缺失 | 前期未统一识别缺口 | 在大纲阶段完整标记所有缺口，前置沟通 |
| 草图省略，直接出图导致布局偏差 | 过度自信视觉设计 | 坚持草图预审，低成本修正布局问题 |

## 📝 文档模板参考
### 通用标准结构（无自定义模板时使用）
#### 1. PRD / SRS 通用结构
```
1. 文档概述
   1.1 编写目的
   1.2 文档范围
   1.3 阅读对象
   1.4 术语、缩略语、参考资料
2. 总体业务描述
3. 功能需求
4. 非功能需求（性能、安全、兼容性、可用性）
5. 外部接口需求
6. 业务约束与合规要求
7. 附录
```

#### 2. 系统/概要设计文档结构
```
1. 文档概述
2. 总体架构设计
3. 功能模块设计
4. 接口设计
5. 数据结构设计
6. 部署方案设计
7. 风险与应对措施
8. 附录
```

#### 3. 详细设计文档结构
```
1. 模块概述
2. 业务流程设计
3. 内部/外部接口定义
4. 数据结构设计
5. 异常与容错处理
6. 配置项说明
7. 附录
```

## 🧩 复杂度适配策略
根据文档规模与素材数量，灵活精简输出形式，**阶段不可省略**：
1. **简易文档**（单模块、1~2 份素材）
   - 简化表格、大纲格式，使用列表/短句呈现
   - 草图可极简，保留核心结构即可
2. **复杂文档**（多模块、5 份以上素材）
   - 完整执行全流程，可拆分内容编写为多轮完成
   - 细化交叉核对矩阵、需求追溯矩阵
3. **同项目复用**（连续编写同系列文档）
   - 素材盘点、模板选择结果可复用（需确认素材无变更）
   - 信息提取、大纲、图表、编写、校验阶段必须重新执行

## 📦 交付物清单
正式交付时，成套输出以下内容：
1. 最终版技术文档（Markdown / Word 等格式）
2. 文档元数据：文档编号、版本、编制日期、完整素材清单
3. 需求追溯矩阵、信息完整性评估报告
4. 图表文件 + 已确认的文本草图
5. 汇总清单：所有 `[TODO]` 待补充项、信息冲突项

## 🤝 贡献指南
欢迎提交 Issue、PR 共同完善这套文档体系：
1. **问题反馈**：在 Issues 提交流程漏洞、规则优化建议、模板补充需求
2. **模板新增**：如需新增行业专属文档模板，请附带使用场景与样例
3. **规则优化**：流程、标记、图表规范优化，需同步说明优化原因与落地方式
4. 提交规范：所有修改需保证**不破坏原有核心原则**（可追溯、不虚构、流程有序）
