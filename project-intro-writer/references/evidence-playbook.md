# 证据源定位与读取要点（Evidence Playbook）

配合 project-intro-writer 技能使用。目标：从项目资料中**高效、真实**地提取撰写证据，不做穷尽式深挖。

## 0. 总原则

- 先扫结构（scripts/scan_project.py），再按档位取文件；用户说"资料够了/别深挖"时立即收敛。
- 忽略 `.$*.bkp`、`.tmp`、`.~lock*` 等编辑器临时/备份文件；`.xmind` 是 zip 包，可当 zipfile 打开读 `content.json`（可选，低优先级）。
- 每个证据摘录时记下**绝对路径 + 大致位置**，正文撰写时标注来源文件名。

## 1. 方案 / 汇报 PPT（第一优先级）

- 用 scripts/extract_office.py 提取 `a:t` 文本（按 slide 分页，带页码）。
- 重点摘录：项目名称与一句话定位、目录结构（往往就是能力框架）、技术参数表、架构图文字、里程碑时间点、团队分工/署名。
- **注意版本**：同名多版本方案（如 `xxx方案(260115).pptx` / `xxx方案(260819).pptx`）以日期最新版为准，旧版仅作对比。

## 2. 系统简介 / 需求确认 docx

- 简介 docx 通常有"主要功能/技术特点"小节，是概述章节的骨架来源。
- 需求确认文档含功能清单、接口约定、数据点表、验收标准，是"核心能力"和"技术架构"的硬证据。

## 3. 设计文档 / 功能设计 md-pdf

- 产品功能设计文档：模块划分、每个模块的输入/输出/算法/阈值/频率——技术细节的最主要来源。
- 摘要式阅读：先读目录与小标题，再精读与"核心能力/指标/阈值"相关章节。

## 4. 数据库备份 .sql（工程资产证据）

- 用 grep/正则定位：`CREATE TABLE` 看表结构；`INSERT INTO "schema"."table" VALUES` 看**已配置的真实数据**（测点数量、锅炉模板、周期分析配置、事件/规则记录）。
- 统计口径示例：`grep -c 'INSERT INTO "abbdata"."point"'` → 测点数；模板表数据 → 已支持机组型号。
- 这是"工程落地深度"的量化证据，比任何形容词都有说服力。

## 5. 源码目录

- 先看依赖清单（package.json / pom.xml / requirements.txt / go.mod）判断技术栈与框架。
- 找算法/模型/规则相关文件（按关键词：algorithm / model / rule / predict / calc / engine），列文件名并简述作用。
- `git log --oneline --pretty="%h %ad %s" --date=short` 看迭代节奏与关键提交。

## 6. 架构图 .drawio

- 用 extract_office.py 提取所有节点 `value` 文本（去重），分层结构（基础设施层/数据层/服务层/展现层）与协议（OPC UA/Modbus/DCS 接口）一目了然。

## 7. 在线演示系统（如用户提供）

- chrome-devtools：new_page → navigate_page（hash 路由如 `#/temperature` 必须导航后 take_snapshot）→ 逐页点导航菜单 → take_snapshot 取文本。
- 记录：页面标题、路由清单、图表类型、指标名称与**实时数值**（这是"系统已上线运行"最硬的佐证）、交互控件、页脚版权。
- list_network_requests 看 `/api` 或 `/v1/...` 接口 URL 与返回结构，佐证后端能力与数据字段。
- 需要登录而无法登录时：如实记录"演示系统需登录，未获取到页面内容"，**不得编造**。
- 截图存 `C:\Users\aaron\AppData\Local\Temp\<项目名>_demo\` 备查，不写入项目目录。

## 8. 常见陷阱

| 陷阱 | 对策 |
|------|------|
| 把 PPT 里的行业通用背景写成自家成果 | 区分"行业背景"与"本项目成果"，后者必须有上线/验收/数据佐证 |
| 多版本方案混用 | 以最新版为准，注明版本日期 |
| 演示系统数值当生产效果 | 演示数据只证明"功能可用"，不得表述为"应用效果" |
| 厂商/客户名泄露 | 默认口径淡化，除非用户明确要求 |
| 效果指标（准确率/提前量）无出处 | 一律"待补充"，列入缺口清单 |
