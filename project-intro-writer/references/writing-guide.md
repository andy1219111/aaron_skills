# 三段式撰写细则（Writing Guide）

配合 project-intro-writer 技能使用。readme.md 正文固定三段式，**中性、瘦身、去来源**优先于详尽与举证。

> 本细则经三个项目迭代校准。第一条原则：**这是一份中性的项目说明文档，不是营销稿，也不是合规举证材料。**

## 章节结构（固定）

```
一、系统概述
  1.1 系统定位（1~2 段主旨描述：系统是用来做什么）
  1.2 核心能力（5 条左右能力描述 + 标准符合性支持一段）
  1.3 技术架构与部署形态（分层、数据来源、接口）
二、解决的业务问题与用户痛点
  2.1 背景（一段，点到为止）
  2.2 用户痛点（分条，具体到运行场景）
  2.3 本系统的对策（与本痛点点对点呼应）
三、目前已取得的成果
  3.1 当前已实现的能力（端到端闭环，6 条左右）
  3.2 已实现的价值（6 条左右）
```

正文控制在 **80~120 行**。超过 130 行说明写成了"举证材料"，需要瘦身。

## 每章写什么

### 一、系统概述

- **1.1 系统定位**：**1~2 段**，主旨描述。第一段讲"面向谁、聚焦什么、整合什么数据"；第二段讲"数据如何组织、业务主线是什么"，末句可带出当前交付范围。**不要**把管理层級、术语口径、交付范围拆成多个要点段。
- **1.2 核心能力**：只写**能力本体**，每类一句话。写"支持 XX 分析"，不写"支持 XX 分析，包括 8 张图表、4 张表格、7 类图层、13 个 KPI 字段"。**严禁**逐一罗列：模块清单、页面清单、字段目录、接口清单、KPI 明细。**不要**写"本期已交付 N 个模块"这类段落。
- **标准符合性支持**（属于 1.2 的最后一段，不是独立章节）：一句话说明系统在数据模型与业务流程层面对相关标准的支持，提及标准名称即可。详见下文"标准与合规的处理"。
- **1.3 技术架构**：按层写的确：总体架构 → 前端/地图服务 → 后端 → 外部集成 → 典型数据组织。技术细节保留（坐标系、版本管理方式、回调机制等），因为是工程说明的一部分。

### 二、业务问题与痛点

- 背景限定在资料提过的范围，一段点到为止，**不铺陈宏观叙事、不引无出处数据**。
- 痛点**具体到运行场景**，不写"提升管理水平"这类空话。
- 对策与痛点点对点呼应，用"-"列表，一条一句。

### 三、已取得的成果

**只写结果与价值**，不写过程。

- **3.1 当前已实现的能力**：按业务链路（如"数据接入 → 专题展示 → 标注沉淀 → 报告输出"）列 5~7 条已具备的能力，每条一句话讲清楚能做到什么。
- **3.2 已实现的价值**：以业务语言说明带来的价值，克制表述。**避免**把价值写成未经证实的量化效益。
- **不写**：里程碑、交付计划、roadmap、版本演进排期、演示环境实测数据（几条管线/几处测点/几份报告）、已交付文档资产清单、"第一步第二步"式建设路径。这些内容属于过程，全部下沉到配套文件。

正式投产、验收、效果量化指标若资料无依据，不写数值，也不在正文留"待补充"字样——直接进入配套文件的缺口清单。

## 标准与合规的处理（重点）

用户明确要求：**无需照搬国家标准条目，只需体现产品对标准的支持。**

- 标准相关内容**降级为 1.2 核心能力下的一段**，标题用"标准符合性支持"，不作为独立章节。
- **不写**：逐条条款枚举（§4.5/§5.3.7/附录 B.6 这种）、"合规要求 → 平台支撑"对照表、"为什么这项能力是刚需"这类论证段、"强制性""硬性义务""自选动作"等判断性措辞。
- **写法**：一句话能力陈述 + 提及标准名称 + 说明在哪些层面（数据版本管理、变更留痕、坐标基准、质量校验、字段口径）已相应体现。标准本身的必要性由读者自行判断，不由我们来论证。

## 措辞纪律

- **正文不出现任何来源标记**：不写"（来源：《xxx.pptx》）"、不放演示链接、不提具体文档名、不写"演示环境实测"。所有出处集中到配套文件。
- 用"支持/实现/具备/已完成"等中性可验证动词；**禁用**"国内领先/极大提升/显著降低/赋能/抓手/告别痛点"等渲染词。
- **禁用判断性与论证性措辞**："必须""硬性义务""不是企业的自选动作"等。中性陈述即可。
- 保留必要的专业术语、型号、算法名、字段名（这些是工程说明的一部分），但不堆叠。

## 敏感口径（默认淡化）

- 默认：开发方、客户名称、硬件/仪表品牌以中性表述替代（"某石油大学"、"第三方测温硬件"）。
- 用户明确要求如实写时按资料原文写，出处记在配套文件。
- 拿不准时问一次（AskUserQuestion），两个选项：如实写 / 淡化。

## 配套文件该装什么

所有"证据、过程、管理"信息一律下沉到 `readme-待补充事项与资料来源.md`：

| 章节 | 内容 |
|---|---|
| 一、待补充事项清单 | 表格：缺失信息 → 用于补充正文哪个章节 → 状态 |
| 二、资料来源清单 | 正文**全部结论**的出处（绝对路径 + 演示系统地址），注明核对过的内容 |
| 三、项目过程节点（内部追溯用） | 原正文删掉的里程碑表、演示环境实测数据（管线数/测点数/报告数等） |
| 四、历次调整说明 | 每次修改的内容与理由，按时间倒序或编号递增 |

文件抬头写一句："正文为中性项目说明，不标注来源，全部出处集中记录于本文件第二章。"

## 交付规范

- 两个文件放项目目录：`readme.md`（正文）+ `readme-待补充事项与资料来源.md`。
- **readme.md 不放"编制说明"块**；末行用引用块一句指向配套文件即可。
- present_files 一次呈报两个文件，等用户确认后再处理下一个项目。

## 接收修改指令的方式

用户习惯给出编号化的修改清单（如"一下修改点，逐项执行：1… 2… 3…"）。执行要点：

1. **逐项对照执行**，不要合并、不要漏项、不要自作主张增加改动；
2. 改完用 grep 自检（例如删除类指令要验证残留为 0，去来源类指令要验证全匹配）；
3. 同步更新配套文件的章节指向与调整说明，保持两个文件一致；
4. 回复中**按用户的编号逐项汇报执行结果**，让用户一眼核对。
