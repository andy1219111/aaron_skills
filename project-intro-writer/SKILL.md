# 项目产品介绍撰写（Project Intro Writer）

## Overview

把用户提供的项目资料目录（可选：在线演示系统地址）转化为一份正式、可交付的产品介绍文档。产出固定为两个文件，均放在项目目录下：

- `readme.md` —— 三段式产品介绍正文
- `readme-待补充事项与资料来源.md` —— 缺口清单（含每项缺口用于补充哪个章节）+ 全部资料来源清单

一次只处理一个项目，用户确认后再进入下一个。

## 核心纪律（不可违背）

1. **真实第一**：每个结论必须有资料出处（文件名级）。无依据的内容不写、不猜、不套模板化表述，一律标"待补充"。
   - 注意：**真实 ≠ 举证**。内容真实即可，不等于正文要逐条展示证据。
2. **有限资料原则**：用户给什么用什么。过滤噪音目录（`.git`/`node_modules`/`.obsidian`/`.venv`/`dist`/`build` 等），只通读关键文档，不做穷尽式深挖。用户明确说过"无需过于深度的扫描"时，立刻收敛。
3. **一次一个项目**：逐个处理，当前项目经用户确认后才开始下一个。
4. **文档定位：中性的项目说明**。这是一份给人看的项目说明文档，**不是**营销稿件，**不是**合规/标准举证材料。因此：
   - 禁止营销式论证（"为什么是刚需""赋能""告别……痛点"）与判断性措辞（"必须""硬性义务""自选动作"）；
   - 第三方标准/国标只**提及支持关系**，不逐条罗列条款号，不做"合规要求 → 平台支撑"对照表；
   - 涉及某项标准或行业背景时，一句话点到为止，不展开论证其必要性。
5. **交付去来源**：核实阶段每句话都要有出处，但**正文不写括注来源、不放演示链接与文档名**；全部出处集中收录到配套文件第二章。用户读到的是干净的正文，核查时看配套文件。
6. **正文瘦身**：核心能力只描述"能做到什么"，**不逐一罗列**现有模块、页面、字段、接口、KPI 清单。系统定位控制在 1~2 段主旨描述。成果章节只写结果与价值，**不写里程碑、计划、roadmap**。演示环境实测数据（一条管线、几处 HCA 这类）属于过程证据，不进正文。
7. **缺口清单化**：缺失信息逐条列出，注明"用于补充哪个章节"，放进配套文件，不自行推断填充。
8. **口径默认淡化**：默认淡化开发方/客户/仪表品牌等敏感名称（除非用户明确要求如实写），下笔前用一次提问确认口径。

> **两文件分工**：`readme.md` = 干净、中性、瘦身的正文（唯一对外交付物）；`readme-待补充事项与资料来源.md` = 所有过程性内容的管理仓库（资料出处、缺口清单、项目过程节点/里程碑、历次调整说明）。凡属"证据、过程、管理"的信息一律下沉到配套文件。

## 工作流

### 第 1 步：确认输入

向用户确认（信息不全时提问，不要自行假设）：

- 项目资料目录（必需，绝对路径）
- 在线演示系统地址（可选；有则必须实测）
- 敏感信息口径（默认：淡化厂商/客户/品牌；选项：如实写 / 淡化）

### 第 2 步：扫描目录，识别关键文件

运行 `scripts/scan_project.py <项目目录>`，得到结构树 + 按优先级分档的文件清单。分类规则见 references/evidence-playbook.md。**不要**通读全部文件，按以下优先级取用：

1. 方案/汇报类：最新版方案 PPT、KICKOFF/启动会 PPT、系统简介 docx
2. 需求/设计类：需求确认文档、产品功能设计、架构图（.drawio）
3. 工程资产类：数据库备份脚本（.sql）、配置清单、源码中的算法/模型文件
4. 其他：git 提交历史、验收/测试记录

### 第 3 步：提取关键文档内容

用 `scripts/extract_office.py` 批量提取 docx/pptx/xlsx/pdf/drawio 文本；.sql 用 grep 看表结构与配置数据；源码看 package.json/pom.xml/requirements.txt 等判断技术栈。提取后通读并摘录与以下主题相关的原文：系统定位、核心能力（含算法/指标/阈值/频率等技术细节）、业务痛点、技术架构、成果与里程碑、参与方。

### 第 4 步：实测在线演示系统（如有）

用 chrome-devtools 工具逐页抓取：导航菜单与路由、图表类型、核心指标名称与实时数值、交互控件、页脚版权。注意 hash 路由（`#/temperature`）需 navigate_page 后 take_snapshot；页面可能需要登录——登录态不可用时如实记录"无法访问"，不得编造页面内容。可用 list_network_requests 核对后端接口与数据字段。截图存临时目录备查。

### 第 5 步：按三段式撰写 readme.md

结构模板见 `assets/readme-template.md`，撰写细则（每章写什么、措辞纪律）见 `references/writing-guide.md`。要点：

- **一、系统概述**：1.1 系统定位（1~2 段主旨描述）→ 1.2 核心能力（5 条左右能力描述，不罗列模块/页面/字段 + "标准符合性支持"一段）→ 1.3 技术架构与部署形态
- **二、解决的业务问题与用户痛点**：2.1 背景（一段）→ 2.2 用户痛点（具体到运行场景）→ 2.3 本系统的对策（与痛点点对点呼应）
- **三、目前已取得的成果**：3.1 当前已实现的能力（按端到端链路）→ 3.2 已实现的价值。**不写**里程碑、交付计划、演示环境实测数据与已交付文档资产

正文目标 80~120 行。撰写细则与措辞纪律见 `references/writing-guide.md`。

### 第 6 步：产出配套文件

按 `assets/pending-info-template.md` 生成 `readme-待补充事项与资料来源.md`：

- **待补充事项清单**：表格列出每项缺失信息、用于补充正文哪个章节、当前状态（待补充）
- **资料来源清单**：正文全部结论的出处文件（绝对路径）+ 在线演示系统地址

### 第 7 步：交付并等待确认

用 present_files 同时呈报两个文件，正文保持干净的三段式（待补充内容只在配套文件管理，用户后续要求合并时再回填）。等用户确认后，接收下一个项目的资料目录，重复本工作流。

## Resources

### scripts/

- `scan_project.py` —— 扫描项目目录：输出分层结构树，过滤噪音目录，按"方案汇报/需求设计/工程资产/其他"四档给关键文件分类打标
- `extract_office.py` —— 统一提取 docx/pptx/xlsx/pdf/drawio 文本为可读纯文本（zipfile + 正则方案，无需额外依赖；pdf 可选 PyMuPDF）

### references/

- `evidence-playbook.md` —— 各类证据源的定位与读取要点（PPT/Word/PDF/Excel/SQL/git/架构图/在线演示系统），含常见陷阱
- `writing-guide.md` —— 三段式撰写细则、措辞纪律、来源标注规范、敏感口径处理、待补充清单规范

### assets/

- `readme-template.md` —— readme.md 正文模板骨架（含编制说明与章节占位）
- `pending-info-template.md` —— 「待补充事项与资料来源」文件模板骨架
