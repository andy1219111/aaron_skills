# 句式模板库与措辞转换表

配合 `SKILL.md` 使用。写的时候直接复制句子、替换〔占位符〕。

---

## 一、句式模板库（10 类）

### 1. 标的句（技术目标开头）
```
应买方委托，卖方应完成〔项目名称〕中"〔模块名称〕"的研究开发、适配优化与成果交付工作，
形成可在〔运行环境〕独立运行的技术成果（以下简称"本成果"）。
```
变体（更强调成果）：`……形成一套具备〔能力A〕、〔能力B〕、〔能力C〕的技术成果。`

### 2. 要件②句（技术目标末尾，必带）

**丝滑版（默认用这个，Aaron 偏好）**
```
上述技术目标所对应的技术方案，非本合同订立时现有技术水平所能直接实现，
需由卖方通过本项目研究开发形成。
```
**原版（当地登记机构字面检索"尚未掌握"时改用）**
```
上述目标所对应的技术方案，在合同订立时尚不为双方所掌握，需由卖方通过本项目研究开发予以实现。
```

### 3. 应用效果句 + 免责句（成套出现）
```
本成果交付并应用后，预期实现〔统一基线/提升达标率/缩短周期/强化防护能力〕，保障〔对象〕
持续稳定运行。前述效果系技术成果应用后的预期技术经济效果，不构成卖方对买方运维工作的
服务承诺。
```

### 4. 能力块句（技术内容，每块统一用这个骨架）
```
一是〔能力块名称〕。本成果面向〔适用对象〕，完成〔做什么〕，形成〔交付后可独立存在的东西〕，
不依赖其他系统或平台即可完成〔作业〕。通过对〔维度〕的检查/处理，输出〔成果物：清单、
报告、指令、结论〕，形成可供买方直接使用的〔依据〕。
```
要点：**每块必须有"输出什么"**，否则能力讲完了没有落点。

### 5. 成果形态限定句（紧跟成果清单表）
```
双方确认，上述成果均为本合同研究开发工作的产出物，其形态限于软件成果、数据成果与文档成果，
不包括设备、仪器、零部件、原材料等货物的供货；上述成果的载体数量以满足买方掌握、使用该
技术成果及必要存档所需为限；上述成果交付时以交付时点的最新版本为准。
```

### 6. 创新性防火墙句（放在创新性列举之前）
```
本项所列创新性，均为本项目研究开发成果（交付物）本身所具备的技术特征，以及该成果投入
使用后为买方带来的收益，不属于研究开发过程中的工作方法描述。
```

### 7. 创新性技术特征句（每项 2 句，只讲结构/机制，不展开收益）
```
一是"〔有名字的机制〕"。上层〔新结构的描述〕；下层〔另一半的描述〕，二者可独立演进。
```

### 8. 现有技术水平句（钉死时间点）
```
本合同订立时，〔领域〕已具备下列成熟做法，其技术水平与局限如下：一是……二是……三是……
四是……。上述做法均为〔具体工具/产品品类，如"通用运维自动化工具、通用配置管理与基线
核查工具以及商用主机安全管理产品"〕所具备的既有能力，构成本合同标的研究开发的现有技术起点。
```

### 9. 本质差异句（防火墙，不可改写）
```
本项目技术方案并非对上述现有技术做简单改变尺寸、参数、排列或类似手段的变换，而是在技术
实现要素上具有下列本质差异：一是在〔方面〕上，以〔新结构〕替代〔旧结构〕，〔要素发生了
什么变化〕；二是在〔方面〕上……。
```

### 10. 验收判定与复测句
```
（三）验收判定与复测。上述 N 项技术指标全部满足的，视为本项目技术指标验收合格；任一项
指标未达标的，卖方应在买方提出异议之日起____日内完成整改并提交复测申请，复测仍不达标的，
按本合同第____条约定处理。前述各项指标的具体测试报告，作为本合同〔验收条款编号〕验收
依据的组成部分。
```

## 二、措辞转换表（服务味 → 成果味）

| 原表述 | 改为 | 原因 |
|---|---|---|
| 全流程研发、落地部署、部署上线 | 研究开发、适配优化与成果交付 | "部署"是专家组最敏感的词 |
| 彻底替代传统人工运维处置模式 | 删除，或改为"形成……自动化作业能力" | 听起来像人力替代型服务合同 |
| 持续降低买方运维成本 | 提升合规达标率与策略一致性、缩短处置周期 | 同上 |
| 集成〔某能力〕 | 形成〔某能力〕 | "集成"是开发动作 |
| 搭载〔某引擎〕 | 形成〔某处置能力〕 | 产品说明书口吻 |
| 自主研发、定制化研究开发 | 保留（有利） | 支撑要件② |
| 调研 | 研究 | "调研"像前期咨询 |
| 常态化、精细化管控 | 自动化 / 标准化 | "常态化"易被读成长期运维 |
| 原型系统 | 系统 / 系统样机 | 全篇统一即可，不必强删 |
| 提供给买方使用 / 交付买方使用 | 向买方交付并转让使用权 | 交付动作要有客体 |
| 筑牢……防线、全方位赋能 | 直接删除 | 空话，稀释信息密度 |
| "在合同订立时尚不为双方所掌握" | "非本合同订立时现有技术水平所能直接实现，需由卖方通过本项目研究开发形成" | 实质不变，去掉刻意感（Aaron 明确指出原句"显得很刻意，不太丝滑"）；当地登记机构字面检索时再换回 |
| 交付节点写具体日期（2026年3月31日） | 写月份周次（2026年3月第四周） | 具体日期=对买方的硬承诺，任一环节延误即触发违约；周次留缓冲。合同**有效期限**仍写具体日期，两者不冲突 |
| 项目建设 / 项目实施 | 本项目研究开发 | "项目建设"是工程口吻 |
| 系统上线、上线运行 | 成果交付与应用 | — |
| 提供 7×24 技术支持 | 成果交付后的技术指导（限定为成果转化辅助事项，不构成独立的合同标的） | — |

### 绝对敏感词 5 个
**部署、实施、运维、售后、服务。** 定稿前在 Word 里逐个检索；命中处要么换词，要么加限定。

### 不能动的 3 类句子
1. "并非简单改变尺寸、参数、排列或类似手段的变换"
2. "不属于研究开发过程中的工作方法描述"
3. "不构成卖方对买方运维工作的服务承诺"

## 三、相邻条款的填空要点（一笔带过版）

### 第三条 研究开发计划 / 进度表
四阶段节点要与第一款成果清单表的交付节点**逐字一致**；表格"阶段"列不要出现 4、4、4、4 这种重复编号。
**节点统一写"某月第 X 周"，不写具体日期**（Aaron 要求）。改节点时记得同步四处，否则三张表对不上：
① 第一款成果清单表"交付节点"列 ② 第三条进度表"交付节点"列 ③ 第十二条成果交付时间
④ 第五条付款条件（不要写"2026年6月30日阶段成果"，改写成"第二阶段成果"）。
合同的**有效期限**（封面）仍写具体日期，与交付节点互不冲突。

### 第四条 买方提供的技术资料及协作事项
- 每项资料必须挂"**用于什么研究事项**"列。不写用途，一张清单看起来就是"买方配合我方实施"。
- 分批提供：输入类资料签约后数日内；测试环境类资料按对应阶段开始前 N 日提供。
- 必带顺延免责：`买方未按期提供致使卖方无法开展相应阶段研究开发工作的，该项工作所对应
  的交付期限相应顺延，卖方不承担因此产生的逾期责任。`
- 协作事项不要写"无"。至少写：指定技术对接人并限期答复 / 提供被测主机接入条件与测试
  时段 / 组织阶段成果书面确认 / **组织专家评审并签订验收报告**（研发项目的标志性动作）。

### 第五条 价款
换算核对：分项之和必须等于合计。曾出现"2,0000"笔误导致凑不平总额——**金额务必验算**。

### 第十二条 交付
交付形式建议统一写明"**含源代码**"。研发合同中交付源代码是强证据，且要与第一款成果
清单表的载体列一致。

### 第十三条 验收
验收依据不要指向已删除的附件或"技术协议"。推荐写法：
`买方按照本合同约定的验收标准与交付要求，组织专家对交付成果进行评审，评审通过后双方
签订验收报告。`

### 第二十五条 术语定义（要件②的法定措辞落点）

**丝滑版（默认）**
```
研究开发标的：指本合同第一条约定的〔成果/模块〕技术方案，该技术方案由卖方通过本项目
研究开发形成并向买方交付，非现有可直接选用的成熟产品。
```
**原版（当地登记机构字面检索"尚未掌握"时改用）**
```
研究开发标的：指本合同第一条约定的〔成果/模块〕技术方案，该技术方案系买方、卖方在
订立本合同时尚未掌握的技术方案。
基准测试环境：指双方于首次测试开始前共同书面确认的测试环境，其构成以双方书面确认的
环境清单为准。
```
注意：若正文用的是"双方书面确认的基准测试环境"，就不要再在术语里写"附件一第 X 项所列
基线环境"，两套定义会打架。

### 第二十七条 其他约定
要件②双保险（丝滑版）：`本项目为技术开发，卖方按本合同约定完成研究开发并向买方交付技术成果；本合同标的所涉技术方案由卖方通过本项目研究开发形成，不属于对现有产品的选用、组合或配置。`
（原版：`合同标的为买方、卖方在订立合同时尚未掌握的"〔模块〕"技术方案。`）
另建议把技术边界防火墙句放在此处（若正文没地方放）：
`本项目卖方不提供通用运维自动化能力，不采购、不集成、不封装任何第三方商用〔品类〕产品，
亦不提供上述产品的实施与运维服务。`

### 第二十四条 争议解决
仲裁机构必须写**具体名称**（如"北京仲裁委员会"），写"买方所在地仲裁委员会"可能因约定
不明被认定无效。

## 三之二、技术方案怎么"体现"在合同里（实测有效写法）

用户通常会另给一份《技术开发方案》。它不能只在正文里被"参考"，要**挂成合同组成部分**并被正文回引，
这样答辩时"你的技术方案在哪"有据可查，也顺带支撑要件①（有明确研发计划）：

1. **第二十六条第 1 项**：`技术背景资料：《〔项目名〕项目技术开发方案》（以下简称《技术方案》）；`
   —— 该条本身即"经双方确认后为本合同的组成部分"，挂进去即可，不必另做附件
2. **第一条第 3 款回引一句**：`本项目技术方法与路线与本合同第二十六条所列《技术方案》一致，具体如下。`
3. **内容融合核对表**（逐项确认方案要点都已进合同，避免答辩被问"方案和合同对不上"）：
   项目背景与现有做法局限 → 第 3 款"现有技术水平"；研发目标 → 第 1 款四项目标；
   总体架构与模块划分 → 第 2 款能力块；关键技术 → 第 3 款技术方法；
   创新性 → 第 2 款创新性技术特征；技术路线阶段 → 第 3 款技术路线；
   技术指标 → 第 4 款指标表；交付成果 → 第 2 款成果清单表；验收方式 → 第十三条；进度 → 第三条

## 四、两个反复出现的坑

**坑 1：同一成果两套命名。**
技术目标里说"自研 A、B、C 三个引擎"，成果清单里却是另外四个名字，评审一对照就会追问。
解决：统一为一套；或在交付条款加一句对应关系说明。

**坑 2：交叉引用编号。**
常见错误是正文只有 4 款却写"见本合同第一条第 6 款"。改稿后务必全局搜索"第 X 款""附件
一""第六条"等引用，逐条核对是否还存在。
