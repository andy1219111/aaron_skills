# 技术开发合同认定改写

## 用途

输入：项目原始合同、技术方案、初审修改意见等资料。
输出：**成果导向**的技术开发合同文本，重点是第一条技术条款，可直接用于技术合同认定登记与专家答辩。

一句话立场：**认定看的是"研发出了什么"和"凭什么算新"，不是"我们怎么干的"。**

---

## 核心认知（动手前必须记住）

### 1. 二十九条里只有第一条决定成败

制式合同第二～二十九条按模板填空即可，不展开。**决定"是不是技术开发合同"的只有第一条四款**，它是完整的证据链：

| 款 | 回答的问题 | 对应要件 |
|---|---|---|
| 技术目标 | 要研发出什么、达成什么能力 | 要件①研发目标 |
| 技术内容 | 成果有什么能力 + 交付什么 + 创新点在哪 | 要件③技术创新 |
| 技术方法和路线 | 怎么研发 + 为什么现有做法不行 | 要件①研发计划 + 要件②尚未掌握 |
| 技术指标和参数 | 干到什么程度算合格、怎么测 | 验收依据 |

### 2. 三要件中要件②最容易被打

- 要件①：**有明确、具体的科学研究和技术开发目标与计划**
- 要件②：**合同标的为当事人在订立合同时尚未掌握的技术方案**
- 要件③：**研究开发工作及其预期成果有相应的技术创新内容**

要件①和③是"你有什么"，写出来就算有；**要件②是"你没有什么"，必须主动举证**。答辩质疑十有八九冲着它来——"这东西市面上不是有吗？"

要件②的三处标准落点（尽量三处都有）：
1. 术语定义条款：「研究开发标的：指……该技术方案系买方、卖方在**订立本合同时尚未掌握**的技术方案」
2. 其他约定条款：「合同标的为双方**在订立合同时尚未掌握**的……技术方案」
3. **技术目标末尾**（位置最值钱，评审第一眼看到）：「上述目标所对应的技术方案，在**合同订立时尚不为双方所掌握**，需由卖方通过本项目研究开发予以实现」

> **丝滑化写法（Aaron 偏好，默认优先用这套）**
> 直白写"尚未掌握"会显得刻意、像在喊口号。要件②要的是这个**事实判断**，不是这四个字。
> 保留实质、去掉生硬字样，用"须经研究开发才能形成／非现有可直接选用／非现有技术水平所能直接实现"承载同一含义：
> - 技术目标末尾：`上述技术目标所对应的技术方案，非本合同订立时现有技术水平所能直接实现，需由卖方通过本项目研究开发形成。`
>   且该句与第 3 款"现有技术水平"形成呼应，比原句更有技术味
> - 术语定义：`研究开发标的：指本合同第一条约定的〔模块〕技术方案，该技术方案由卖方通过本项目研究开发形成并向买方交付，非现有可直接选用的成熟产品。`
> - 其他约定：`本项目为技术开发，卖方按本合同约定完成研究开发并向买方交付技术成果；本合同标的所涉技术方案由卖方通过本项目研究开发形成，不属于对现有产品的选用、组合或配置。`
>
> **风险提示**：个别地区认定登记系统仍在字面检索"尚未掌握"。若被退回，补回原句式即可，只改技术目标末尾一处成本最低。交稿时把这个取舍明确告诉用户。

### 3. 全程贯穿主线三问

撰写时必须逐项回答，且各司其职不重复：

| 问 | 落点 | 写法要求 |
|---|---|---|
| **创新点** | 技术内容 | 必须是**技术结构**，不是形容词。前置防火墙句：「本项所列创新性，均为本项目研究开发成果（交付物）本身所具备的技术特征……**不属于研究开发过程中的工作方法描述**」 |
| **与普通/常规技术或工具有何不同** | 技术方法和路线 | 「现有技术水平（本合同订立时的技术起点）→ 本质差异 → 差异对照表」三段式 |
| **能带来什么** | 技术内容末尾成效对比表 + 技术目标应用效果句 | 效果句后必须跟免责句：「前述效果系技术成果应用后的预期技术经济效果，**不构成卖方对买方运维工作的服务承诺**」 |

### 4. 两条硬规矩（差异写法，答辩被问最狠的地方）

**① 对立面必须具体到某一类工具/产品。**
✅ "通用批量运维工具""静态加固脚本库""上层统一＋底层条件分支硬编码"
❌ "传统方式""现有方案" —— 专家会认为你在回避。

**② 差异必须落在技术实现要素上，不能落在效果上。**
✅ "由'脚本与操作系统一对一绑定'变为'原语—规则—原生指令'三层映射，差异收敛于规则层"
❌ "由人工操作变为自动执行" —— 这是效率改进，正是服务合同的画像。

## 工作流程

### Step 1：读资料，先列素材清单

从原始合同/技术方案中提取四类信息，缺什么标"待补"：
- 研发目标与要解决的问题
- 现有技术的做法与局限（**这是要件②的弹药，必须挖出来**）
- 拟采用的方法、阶段划分
- 可量化的指标数值

### Step 2：确认结构约束（必须问）

制式合同**不得自行扩展第一条的款数**。第一条固定只含四款，多出来的内容只能就近并入：

| 内容 | 并入哪款 |
|---|---|
| 现有技术水平与本质差异 | → 技术方法和路线 |
| 研究开发成果清单与交付形态 | → 技术内容 |
| 成果的创新性、收益与对比优势 | → 技术内容 |
| 测试条件与验证口径、验收判定 | → 技术指标和参数 |

指标款不要塞创新性，会长到没人读。

### Step 3：逐章节改写，一次一款，用户确认后再往下

**不要一次全篇改完。** 改完一款交用户确认口径，避免整篇返工。这是本技能最重要的一条协作纪律。

每款交付时：**直接打印改写内容，不修改现有文档**（除非用户明确要求）。

### Step 4：穿插处理相邻条款

第一条定稿后回填相邻条款：交付清单、进度表、买方技术资料清单及协作事项。原则是**每一项资料都挂"用于什么研究事项"**——不写用途，清单看起来就是"买方配合我方实施"。

### Step 5：通篇评审

按 `references/checklist.md` 跑一遍，输出「必须修 / 建议改 / 顺手改」三级清单。

## 第一条四款的写作公式

> 完整句式模板库与措辞转换表见 `references/formulas.md`。

### 【第 1 款】技术目标

```
段1  标的句：应买方委托，卖方应完成〔项目〕中〔模块〕的**研究开发、适配优化与成果交付**
     工作，形成可〔运行环境〕**独立运行**的技术成果。本成果面向〔场景/对象〕，
     通过自主研发〔关键部件〕，形成一套具备〔能力A、B、C〕的技术成果。
段2  目标句：本成果应实现以下目标：一是……；二是……；三是……；四是……。
     **收尾必带**：上述目标所对应的技术方案，在合同订立时尚不为双方所掌握，
     需由卖方通过本项目研究开发予以实现。
段3  效果句：本成果交付并应用后，预期实现〔统一/提升/缩短/强化〕……
     **必带免责句**：前述效果系技术成果应用后的预期技术经济效果，
     不构成卖方对买方运维工作的服务承诺。
```

**铁律：只写目标，不写内容。** 方法、路线、指标、具体数值一律不许提前出现——一旦写进去，四款会互相稀释，用户会叫停。

### 【第 2 款】技术内容

```
段1  总述：本成果的技术内容包括〔A、B、C、D〕四个部分，各部分内容如下。
段2+ 能力块 ×N（每个"一是/二是"一块）：
       一是〔能力块名称〕。本成果面向〔适用对象〕，完成〔做什么〕，
       形成〔交付后可独立存在的东西〕，不依赖其他系统或平台即可完成〔作业〕。
       ── 每块必须有"输出什么"（清单/报告/指令/结论），这是成果导向的核心
段N  成果清单表：序号 | 技术成果名称 | 成果形态 | 载体形式与数量 | 交付节点
       ＋限定句：上述成果形态限于软件成果、数据成果与文档成果，
         不包括设备、仪器、零部件、原材料等货物的供货
段N+1 防火墙句 ＋ 创新性技术特征 ×N（每项 2 句，只讲新结构/新机制）
段N+2 综合成效对比表：对比维度 | 不采用本成果（现有方式） | 采用后 | 量化成效
```

### 【第 3 款】技术方法和路线

```
【技术方法】×N
    一是〔方法名〕。针对〔具体问题〕，研究〔采用的方法〕，
    形成〔该方法产出什么〕。该方法解决〔什么原有缺陷〕。
    ── 动词用"研究"，不用"调研"（调研像前期咨询）
    ── 专业技术名词保留但要配一句中文解释，保住研发深度又让非技术人员读得下去

【技术路线】
    总起：本项目按 N 个阶段顺序推进，前一阶段的产出构成后一阶段的研发基础……
    阶段 ×N：〔阶段名〕。开展〔做什么〕……。**本阶段形成〔阶段成果〕。**
    ── 每阶段末尾必须有一句"本阶段形成……"，把过程收口到成果

【现有技术水平与本质差异】（并入本款）
    （一）现有技术水平：本合同订立时，〔领域〕已具备下列成熟做法，
         其技术水平与局限如下：一是……二是……三是……四是……
         上述做法均为〔具体工具/产品品类〕所具备的既有能力，
         构成**本合同标的研究开发的现有技术起点**。
    （二）本质差异：**并非对上述现有技术做简单改变尺寸、参数、排列或类似手段的
         变换**，而是在**技术实现要素**上具有下列本质差异：一是在〔方面〕上，
         以〔新结构〕替代〔旧结构〕，从而实现〔根本性变化〕……
    （三）差异对照表：对比维度 | 现有技术做法 | 本项目技术方案 | 本质差异
```

### 【第 4 款】技术指标和参数

```
（一）技术指标表：序号 | 技术指标 | 指标要求
      ── 编号必须与下方口径段严格一一对应
（二）测试条件与验证口径
      段1 总述（测试条件）：本款所列技术指标，均指本项目成果在**基准测试环境**下，
          按双方共同确认的**《验收测试方案》**所载……取得的指标值。基准测试环境指
          双方于首次测试开始前共同书面确认的测试环境……一经确认不得单方变更。
      段2 通用取值规则（原文通常没有，必须补）：
          性能类 = 不少于 N 次连续测试取算术平均值 + 最大值不超指标 20%；
          准确率/覆盖率类 = 一次完整测试为准；
          非成果本身原因未完成的不计入分母，可补测，上限两次。
      段3 分项口径 ×N，每条独立成段：
          （1）〔指标〕〔数值〕，指〔精确定义〕，其比率为〔分子〕与〔分母〕之比，
              分母不含〔明确排除项〕。
          ── 每条必须定义三件事：分母是什么、以什么为基准、怎么算通过
（三）验收判定与复测：
      上述 N 项技术指标全部满足的，视为验收合格；任一项未达标的，卖方应于买方
      提出异议之日起____日内完成整改并提交复测申请，复测仍不达标的，按本合同
      第____条处理。前述测试报告作为验收依据的组成部分。
```

**为什么光学指标表不行**：没有口径，"适配覆盖率 100%"的分母是谁、"抽多少样本算 99.5%"必然各执一词；专家看到一表格 100% 却无口径，第一反应是"指标空洞不可验证"，反而减分。

## 措辞红线（一句话版）

**绝对敏感词（定稿前在 Word 逐个检索）：部署、实施、运维、售后、服务。**

高频替换：

| 原表述 | 改为 |
|---|---|
| 落地部署、部署上线 | 成果交付 / 在买方环境中的安装与验证 |
| 研发服务费 | 研究开发经费 / 技术开发费 |
| 售后服务、技术服务 | 成果交付后的技术指导、成果转化辅助义务 |
| 定制开发 | 面向〔场景〕的定制化研究开发 |
| 常态化、精细化管控 | 自动化 / 标准化（"常态化"易读成长期运维） |
| 集成〔某能力〕 | 形成〔某能力〕（"集成"是开发动作） |
| 搭载〔某引擎〕 | 形成〔某能力〕（产品说明书口吻） |
| 调研 | 研究 |
| 原型系统 | 系统 / 系统样机（全篇统一即可，不必强删） |
| 技术栈名词堆砌（前端框架、包管理器名等） | 改为中文能力描述；技术路线只保留 SSH/WinRM 等协议名 |

完整表见 `references/formulas.md`。

## 输出纪律（Aaron 明确要求的）

1. **直接打印改写内容，不修改现有文档**，除非用户明确要求改文件。
2. **纯段落版**：段内用「（一）（二）（三）」或「一是二是三是」编号，方便直接粘进 Word 不破坏格式。表格另行给出。
3. **不越界**：用户给的是哪一章就改哪一章。不要替他写后面的章节（曾因在技术目标里写指标被叫停）。
4. **交付物要短**。非核心部分一律"一笔带过"，只给结论不展开。用户说"不需要写这么多"时立即收窄范围。
5. **法律防火墙句一个字不要动** —— 包括"并非简单改变尺寸、参数、排列或类似手段的变换""不属于研究开发过程中的工作方法描述""不构成卖方对买方运维工作的服务承诺"。这类句子是刻意写的，做可读性优化时保留原文。

## 自检清单（交稿前必跑）

见 `references/checklist.md`。

其中决定成败的 5 问：
1. 要件②是否三处落点齐全？技术目标末尾那句是否还在？
2. 创新性前是否有"不属于工作方法描述"防火墙句？
3. 差异对照表的对立面是否具体到某一类工具/产品？差异是否落在技术实现要素而非效果？
4. 九个敏感词是否全文检索清零？
5. 三张表（成果清单表 ↔ 进度表 ↔ 付款条件表）是否逐字一致？
